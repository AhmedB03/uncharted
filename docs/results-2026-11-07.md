# Uncharted: does building "alien" combinations produce more novel software? (2026-11-07)


> Paths under `results/`, `factory_out/`, `data/` and `repos_big/` are local run outputs (gitignored); the
> commands that regenerate them are listed under Files.
Builder: Claude Haiku 5.5 (4 fix iterations). Spec writer: DeepSeek v4-flash. Blind judge: Claude Sonnet 5.5
(the judge never sees the arm, the atoms used to pick the idea, or the spec's "why unusual" text).

## 1. First attempt: the baseline was broken

n = 100 ideas per arm. Alien = top Alien-sampler triples; "common" = triples that co-occur in a repo
of the 298-repo training corpus.

| stage | measure | common | alien | p |
| --- | --- | --- | --- | --- |
| build | build rate | 85% | 87% | 0.74 |
| combo | novelty | 2.26 | 2.29 | 0.91 |
| spec | novelty | 1.94 | 1.89 | 0.54 |
| code | novelty | 1.93 | 1.93 | 0.96 |

A tie everywhere, because the corpus is too small: 95% of triples occur in exactly one of 298 repos,
so "common" was not common (77 of 82 "common" triples had support 1).

## 2. A bigger corpus

Collected 2,995 popular repos (10x), atomized them with the same model as the originals (Gemini 3.1
flash-lite) and mapped atoms onto the existing 80 clusters by nearest centroid (97.5% agreement with the
original labels; no re-clustering, no retraining). `data/support_big.json`.

The sampler's top picks are not reliably rare: on the 1,681 repos it never saw, 34% of the top-100
alien triples already exist, vs 21% of the old "common" triples and 4% of random triples. Only 166 of the
top 300 alien triples occur in none of the ~3,000 repos.

## 3. Proper comparison: verified-alien vs truly common

Verified-alien = top-300 sampler triples with **zero** support in 2,971 repos. Truly common = triples
with the highest support (3 to 12 repos). n = 100 per arm.

| stage | dimension | common | verified alien | diff | p (Mann-Whitney) |
| --- | --- | --- | --- | --- | --- |
| build | build rate | 86% | 91% | +5 pts | 0.91 (one-sided, common > alien) |
| combo | novelty | 1.94 | 2.60 | **+0.66** | **0.0002** |
| combo | coherence | 3.87 | 3.28 | **-0.59** | **0.0003** |
| combo | potential | 2.49 | 2.62 | +0.13 | 0.17 |
| spec | novelty | 1.88 | 2.05 | +0.17 | 0.019 |
| spec | realness | 3.28 | 3.57 | +0.29 | 0.08 |
| code | novelty | 1.85 | 2.03 | **+0.18** | **0.006** |
| code | substance | 2.30 | 2.43 | +0.13 | 0.10 |
| code | total (5 dims) | 11.01 | 11.55 | +0.54 | 0.05 |

Content filter (OpenRouter refused to judge some proxy/TLS/QUIC combos): combo judge excluded 13 common
and 22 alien; spec 1 common; code none.

**Findings**

1. Verified-unbuilt combinations really are judged more novel (+0.66 on a 5-point scale, p = 0.0002), at
   the price of being less obviously coherent (-0.59). That is the Alien paper's trade-off, now measured.
2. They are no harder to build: 91% vs 86%.
3. The novelty edge survives into the shipped code (+0.18, p = 0.006), but about 73% of it is lost at the
   spec stage (+0.66 -> +0.17). The build stage loses almost nothing more.
4. Everything is still low in absolute terms (novelty ~2/5): these are small stdlib-only projects, and the
   builder fakes about a point of realness (spec realness ~3.5 -> code fidelity ~2.4).
5. Checking against a big corpus is what makes the alien arm work; the sampler alone (trained on 298 repos)
   does not find unbuilt combinations reliably.

## 4. Fixing the spec stage (`results/spec_experiment.md`)

The 20 verified-alien combos the combo judge rated most novel (combo novelty 4.0), re-specced with a stricter
"v2" prompt (name the closest existing tool and beat it; implement every technique for real, no "simulated"
stand-ins; 400-900 lines). Same builder (Haiku 5.5). Each idea is compared with its own original
v1/DeepSeek spec and build (paired sign test).

| spec writer | stage | novelty | ambition / substance | integration | realness / fidelity | built |
| --- | --- | --- | --- | --- | --- | --- |
| DeepSeek, v2 prompt | spec | +0.00 | -0.05 | -0.10 | -0.45 | 17/20 |
| DeepSeek, v2 prompt | code | +0.00 | -0.18 | -0.12 | -0.41 | |
| **Sonnet 5.5, v2 prompt** | spec | **+1.16** (p<0.001) | **+1.21** (p<0.001) | **+1.42** (p<0.001) | +0.68 (p=0.01) | 14/19 |
| **Sonnet 5.5, v2 prompt** | code | **+1.07** (p=0.001) | +0.50 | **+0.79** (p=0.006) | +0.71 | |
| Sonnet specs, **Gemini 3.8 judge** | code | **+1.36** (p<0.001) | +0.79 | +1.00 | +1.21 | |

- The prompt alone does nothing (DeepSeek v2 is flat or slightly worse). **The spec model is the lever.**
- Sonnet-written specs keep the novelty all the way into Haiku's code: code novelty 2.1 -> 3.2, and the
  best builds now score 16-17/25 (the old benchmark's projects averaged ~11).
- An independent judge from another lab (Gemini 3.8 flash, also blind) agrees and sees a larger gain, so this
  is not Sonnet preferring its own specs (`results/crossjudge_gemini.json`).
- Cost: bigger projects (650 vs 330 lines) are harder to build: 14/19 with up to 8 fix iterations (9/18 at 4).
  Also found and fixed: the builder's 8000 output-token cap truncated big projects before their tests.
- Best builds to look at: `factory_out/spec_exp_v2_sonnet/projects/` — awesome-lens, suite-gated-code-rag,
  colpath-sync-planner, priceawesome, gradlens.

**Caveat:** 20 ideas, picked as the most novel combos; the code comparison only covers the 14 that built in both
versions, so the hardest specs are missing from it.

## 5. Recommended next steps

1. Make Sonnet + v2 the default spec writer for the factory, give builds 8 iterations, and keep the
   zero-support corpus check as a gate for "alien".
2. Run the same pipeline on the remaining ~150 verified-alien combos (~$5-6) to get a candidate pool,
   then gate on code judge fidelity >= 3 and total >= 15.
3. Review the top handful by hand before any publishing (publishing is outward-facing: ask first).

## 6. Top-50 run and hand review

Ran Sonnet+v2 specs (8 build iterations) on the next verified-alien combos under a $2 cap ($1.47 used):
26 built in total, 22 code-judged (4 new builds unjudged: routedrift, tagfacet-live, epochsearch, mergeflow).
Eight builds score >= 16/25; best is restwire-lab (18).

Hand review (tests re-run locally, code read):
- **restwire-lab** (REST API + concurrency models + QUIC/KCP transports, 1,000 lines, 17 tests): real QUIC-style
  packet numbers / ACK ranges / threshold loss detection and a real KCP-style RTO + in-order reassembly over a
  seeded lossy virtual link. `compare` on a two-writer If-Match scenario with packet 0 dropped shows the point:
  under KCP (head-of-line blocking) client A wins and B gets 412; under QUIC (independent streams) B overtakes and
  wins. Compare with the v1 build of a similar combo, whose "KCP" just reversed a list.
- **gradlens** (incremental parsing + plugins + autodiff, 750 lines, 16 tests): lossless syntax tree with
  incremental reuse, reverse-mode tape, plugins that add operators to both the grammar and the derivative rules,
  and a gradcheck that catches bad derivative rules.
- awesome-lens, suite-gated-code-rag, colpath-sync-planner: all tests pass; judge notes real but small cores
  (suite-gated-code-rag's crypto is hand-rolled and in-process only).

Still single-file, stdlib-only demos, not production tools: the honest description is "small, genuinely
working prototypes of combinations nobody has built", which is what the method promises.
